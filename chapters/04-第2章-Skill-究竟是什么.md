# 第2章 Skill 究竟是什么

一眼看懂：普通聊天 vs 写一次就能一直用的 Skill 一份 SKILL.md 里，四块内容各管一件事 ① 头部信息 name / description 平台靠它判断：什么时候该调用我 ② 执行步骤 把顺序写死，不让 AI 自己猜 ③ 边界红线 决定它什么时候必须停下来问你 ④ 输出约定 下一步接得住，才算交付
先读什么 → 做什么 → 交什么不能编、不能越权、缺料要停候选表 / 推荐 / 补料清单写文件的人，要把“我为什么退回”写进去；只写“专业、高效”，等于什么都没写。
图 2 标题工作台：名称、用途与执行方法写进同一份说明。
把它与一次临时聊天放在一起看，区别就清楚了。临时聊天里，你可能连续补充“别这么夸张”“不要编经历”“保留具体工具名”。技能里，这些反复出现的要求被组织成稳定步骤；下次换一篇文章，仍然可以使用。需要调用工具时，再由工具完成文件或图片的具体处理。 一个技能通常不只有文字，也可以带参考材料、模板和程序。

比如标题任务需要文章及事实边界；视频任务需要镜头、声音和素材处理方法；文档任务需要样式和检查。不同任务的配套条件不一样，不能看见一个说明文件就断言任何电脑都能跑。

## 用一个例子分清四件事

上一张表是按角色分的，落到一次具体任务里，只要盯住四件事就够了。 假设你要把一篇文章做成视频。专家帮助判断什么值得讲，Skill 说明怎样把稿件变成分镜和作品，工具负责生成声音、处理图片和导出文件，材料提供文章事实和可用画面。四者少了任何一项，都可能影响最终结果。

 一个“视频专家”如果只给了脚本，还没有完成视频；一个“剪辑技能”如果没有可用的剪辑工具，也不能完成导出；有了工具但没有合法可用素材，同样不能直接交付。把这几件事拆开，你就知道该补的是什么，而不是反复要求 AI 更努力。 怎么选第一个任务？我会看三件事：最近还会不会做，材料能不能拿到，结果自己能不能判断。

比如你每天都要处理会议文字，手上也有记录，整理得对不对一眼能看出来，就适

合开始。反过来，完全不懂的行业报告，连数字错了都看不出来，先别把它当第一站。你要借 AI 放大已有经验，起步时不必给自己加一道陌生业务的难题。
💬 发给 AI 的指令（可直接复制）
当任务没有做完，先回答：是我没给清楚材料？是方法说明不完整？是工具或账号不可用？还是结果做出来了，但没有按标准检查？请指出具体证据，不要只评价自己“能力不足”。

## 文件结构，只记住最小的一组

文件结构先别记太多。你只要知道：SKILL.md 放核心做法，需要补充的例子、参考和工具另放。这也是 Agent Skills 格式规范的基本组织方式。刚开始，一个说明文件加一份练习材料就可以做起来，等任务真的需要，再增加目录。不要把搭文件夹，当成了开发能力。

 可以先建立一个“标题小助手”目录，里面放技能说明、一篇练习文章和一次输出记录。 这个版本已经足以帮助你研究输入、步骤和结果。等到规则稳定，再讨论怎样导入自己的工作平台。 “零基础能开发”并不等于完全不用理解结果。

你可以让 AI 写文件，但要知道文件是干什么的；可以让 AI 准备程序，但要知道程序会改哪些东西；可以让 AI 检查，却不能把它的一句通过当作所有问题都已解决。 试着用一句话介绍你的技能：“它拿到什么，帮谁完成哪一段工作，最后交什么。”这句话如果说得绕，先缩小范围。

能把一件小事讲明白，比给一个什么都做的助手起个厉害名字， 更接近真正会用 AI。

## 第3章去哪里寻找别人做好的优质 Skill

这一章，你会拿到
- 一张研究卡：输入、步骤、输出、依赖、验证过什么
- 一次自己动手的小实验，用你的材料跑一遍
- 一条结论：这个做法能不能搬到你的任务上
- 找一个能看见过程的分享

找别人做好的 Skill，我先看一件事：能不能看见它到底怎样做。只有一个漂亮结果、一句“全自动完成”，还不够。我要知道开始时给了什么，中间经过哪几步，最后留下什么文件。你要借鉴的是做事的方法，光看热闹，带不回自己的工作里。
